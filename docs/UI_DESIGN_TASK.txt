BotForge Android UI 全面设计与改造任务

你现在是一名资深 Android UI/UX 设计师和 Kotlin Android 工程师。请负责 BotForge 项目的 UI 设计与实际代码改造。

项目地址：https://github.com/a2006-dev/BotForge

一、项目定位

BotForge 是一个 Android 原生 QQ 官方机器人客户端，同时计划围绕它建立 Plugin / Skill / Tool / Term 开发者社区生态。

需要明确区分两个层次：

1. BotForge 主程序：面向普通使用者，负责机器人连接、Bot 管理、人设、模型、日志、运行状态和基础配置。界面应该简洁、成熟、直观。
2. BotForge 社区生态：面向插件开发者和高级用户，涉及插件管理、权限控制、终端、审计、调试等专业功能。界面可以具有更高的信息密度，但不能让普通用户感到复杂。

本次任务的核心是 BotForge Android 主程序的 UI 设计与改造，同时为社区生态相关页面建立统一的视觉规范。

不要把整个 App 做成开发者 IDE，也不要把社区生态的复杂功能全部堆到首页。

二、设计目标

我希望 BotForge 呈现出成熟商业软件的视觉品质。

设计关键词：

- Premium
- Minimal
- Professional
- Modern Android
- Dark UI
- Clean Typography
- Consistent Design System

视觉方向：

- 以深石墨色、深灰色作为主要背景。
- 使用不同层级的深色 Surface 区分内容区域。
- 使用克制的蓝色作为品牌强调色。
- 绿色用于正常运行、连接成功等状态。
- 红色用于错误、危险操作和异常状态。
- 避免大面积渐变、炫光、玻璃拟态和过度装饰。
- 卡片、按钮、输入框、列表、图标保持统一的圆角和间距规范。
- 合理使用留白，避免界面拥挤。
- 动效轻量、自然，不为了动画而动画。
- 图标尽可能统一使用 Material Symbols 或 Material Icons，不混搭大量风格不同的图标。

整体应当有自己的品牌辨识度，而不是简单套用某个现成 App 的界面。

三、重要技术约束

在开始编码前，先完整检查项目：

- 当前 Activity 和页面结构。
- XML 布局及自定义 View。
- 当前导航方式。
- 现有主题、颜色、字体、图标资源。
- Bot、Persona、Model、Log 等业务模块。
- 当前 Kotlin、AGP、compileSdk 和依赖版本。

技术原则：

1. 不进行全量 Jetpack Compose 重写。
2. 已有 Activity 保留，优先通过 XML、View 和 Material Components 改进。
3. 新增复杂页面使用 Jetpack Compose，采用 ComponentActivity + setContent。
4. Compose 页面使用 ViewModel、StateFlow 和 Repository 管理状态。
5. UI 不应直接操作 BotService、BotManager 或底层 Config。
6. 不要为了 UI 改造破坏现有业务逻辑。
7. 不要擅自更换项目架构、依赖版本或最低 Android 版本。
8. 如果新增 Compose 依赖，必须与项目当前 Kotlin 版本兼容。
9. 保持 View 和 Compose 的设计语言一致。
10. 不允许使用大量硬编码颜色、尺寸和重复组件，应建立统一设计规范。

四、页面设计要求

1. 首页 / 连接状态

这是整个 App 最重要的页面。

重点展示：

- QQ Bot 连接状态。
- 当前机器人信息。
- 服务运行状态。
- 启动 / 停止控制。
- 最近错误信息。
- 重连次数。
- 必要的运行状态信息。

设计要求：

- 连接状态应该一眼可见。
- 正常状态与异常状态要有明显区别。
- 启动、停止等关键操作需要清晰。
- 不要堆砌无意义的数据统计。
- 不要为了美观隐藏重要的运行信息。

2. Bot 管理

展示已配置的机器人列表。

需要有：

- Bot 名称。
- 运行状态。
- 基础信息。
- 添加、编辑、删除入口。
- 清晰的空状态。
- 合理的列表布局。

3. 人设管理

展示人设列表，支持：

- 人设名称。
- 简介。
- 编辑。
- 删除。
- 新建。
- 人设内容编辑。

编辑界面应注意长文本输入体验，避免将复杂文本全部塞进狭小输入框。

4. 模型管理

支持：

- 模型列表。
- 模型名称。
- 服务商。
- API 配置。
- 默认模型标记。
- 添加、编辑、删除。
- API Key 等敏感配置的安全展示。

API Key 默认应隐藏，提供显隐控制。

5. 分组管理

按照现有业务能力设计分组管理界面，保持简洁、清晰。

6. 日志页面

在现有日志功能上改进：

- 日志分类。
- 等级区分。
- 时间信息。
- 过滤和搜索。
- 日志详情。
- 导出功能。
- 空状态和错误状态。

日志页面应偏向专业诊断工具，但不能牺牲可读性。

7. 设置页面

设置页面应有清晰的分组结构，例如：

- 基础设置。
- 服务与保活。
- 权限管理。
- 安全设置。
- 社区生态。
- 关于 BotForge。

不要将所有设置平铺在一个长页面里。

8. 社区生态相关页面

这些页面是社区生态能力在主程序中的入口，不代表要建设在线插件商店。

根据规划书设计：

插件管理页面

- 插件列表。
- 插件名称、作者、版本。
- 启用 / 禁用。
- 权限标签。
- 本地导入。
- 插件来源和信任等级。

插件详情页面

- 插件介绍。
- README 展示。
- 版本信息。
- 权限清单。
- 配置表单。
- 试运行入口。
- 启用 / 禁用操作。

执行权限设置

- 执行权限档位。
- 用户白名单。
- 绑定码。
- 总开关。
- 危险操作确认。

终端 / 任务输出页面

- 任务执行状态。
- 命令输出。
- 标准错误输出。
- 执行耗时。
- 超时和失败状态。

审计日志页面

- 操作来源。
- 操作时间。
- 操作对象。
- 权限判定结果。
- 执行结果。

记忆管理页面

- 记忆内容查看。
- 记忆删除。
- 清理操作。
- 清晰的隐私提示。

这些页面遵循规划书中的功能边界，不要擅自增加在线商店、支付、插件分成等功能。

五、导航与信息架构

不要未经分析就增加底部四栏或五栏导航。

先分析当前 MainActivity 的结构，尽可能保留现有导航习惯。

建议：

- 高频功能保持容易访问。
- 低频配置放入设置。
- 社区生态功能统一放在设置中的生态入口。
- 页面层级清晰。
- 返回行为符合 Android 使用习惯。

不要为了追求所谓现代感而牺牲实际操作效率。

六、设计系统

请建立统一的 Design System，至少包含：

1. Color Palette
2. Typography
3. Spacing
4. Corner Radius
5. Elevation / Surface
6. Button Styles
7. Input Styles
8. Card Styles
9. List Item Styles
10. Status Indicators
11. Dialog / Bottom Sheet
12. Empty State
13. Loading State
14. Error State

优先将设计规范抽象为可复用资源和组件。

XML/View 与 Compose 应共享相同的视觉规范。

七、交互细节

请特别注意：

- 点击反馈。
- 页面切换。
- 加载状态。
- 空状态。
- 错误状态。
- 删除确认。
- 危险操作二次确认。
- 长文本展示。
- 输入框焦点与键盘行为。
- 小屏幕适配。
- 深色主题下的对比度。
- Android 系统状态栏、导航栏和边缘到边缘显示。

不要只设计正常状态，每个重要页面都应考虑加载、空数据、异常和禁用状态。

八、实施流程

不要一开始就大规模修改代码。

请严格按照以下顺序执行：

第一步：项目审查

检查项目现有 UI、导航、主题和业务逻辑，列出当前页面及对应文件。

第二步：设计方案

给出完整的 UI 信息架构、视觉规范和页面设计方案。

第三步：制定改造清单

明确每个页面：

- 保留哪些文件。
- 修改哪些文件。
- 新增哪些文件。
- 是否需要新增 Compose。
- 是否涉及业务逻辑变更。

第四步：分阶段实现

优先完成：

1. 全局主题与设计系统。
2. 首页连接状态。
3. 日志页面。
4. Bot、人设、模型、分组页面。
5. 设置页面。
6. 插件管理与插件详情。
7. 权限、终端、审计和记忆页面。

注意：页面改造顺序不代表项目功能开发路线可以随意调整。必须遵守规划书中的阶段依赖，不能因为 UI 容易实现就提前开放尚未完成的功能。

第五步：验证

- 编译整个项目。
- 检查所有页面导航。
- 检查现有业务功能是否正常。
- 检查不同屏幕尺寸。
- 检查深色主题。
- 修复 UI 溢出、错位和状态显示问题。

九、明确禁止的事情

- 不要全量重写 Compose。
- 不要擅自改变业务逻辑。
- 不要删除现有功能。
- 不要虚构尚未实现的功能。
- 不要用静态假数据冒充真实业务状态。
- 不要为了 UI 漂亮而隐藏错误信息。
- 不要擅自引入大型 UI 框架。
- 不要增加规划书明确排除的在线插件商店。
- 不要一次性生成大量无法维护的代码。
- 不要只给设计建议而不落实代码。

十、最终交付

完成后提供：

1. UI 改造前后的结构说明。
2. 设计系统说明。
3. 修改和新增文件清单。
4. 每个页面的实现情况。
5. 新增依赖及原因。
6. 编译结果。
7. 尚未完成的页面和原因。
8. 已知问题。

最终设计目标：

BotForge 主程序应该是一款成熟、简洁、专业的 Android 机器人管理产品；社区生态功能应该具有开发者工具的专业性。

两者拥有统一的品牌视觉，但不需要相同的信息密度。

请优先保证视觉一致性、真实业务状态、操作体验和代码可维护性，而不是单纯追求炫酷效果。
